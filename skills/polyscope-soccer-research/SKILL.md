# PolyScope Soccer Research

PolyScope is a lightweight PayBox and Polymarket MCP integration. It returns structured provider evidence and deterministic calculations. The agent owns research interpretation, browser use, probabilistic reasoning, and recommendations. API gaps are prompts to continue research, not a reason to stop or a trading eligibility rule.

## Workflow

1. Identify the exact fixture, competition, home and away teams, and UTC kickoff. Use `research_soccer` for the football-data.org fixture and available recent results. Preserve the returned provider IDs as provider-specific identifiers.
2. football-data.org is the primary fixture/results/form provider. If that request fails or returns an unusable response, `research_soccer` makes one API-Football fixture-list request for one UTC date. A valid HTTP 200 empty result is not treated as a provider outage. If `days > 0`, read `fallbackProvider.coverage`: it lists the inclusive requested range, queried day, unqueried dates, completeness, and the continuation instruction. `PARTIAL_FALLBACK_MATCHES` is not full-range coverage. Continue by calling `research_soccer` for each unqueried date with `days: 0`; PolyScope does not automatically issue more date requests. If an explicit `date` range and `fixtureIdentity` are supplied, the identity kickoff must fall inside that range. If the request used a football-data.org `fixtureId`, never use that number to select an API-Football fixture; provide `fixtureIdentity` with exact home team, away team, and UTC kickoff when known. API-Football IDs appear in `fallbackFixtures` under provider-qualified fields and never populate football-data.org IDs.
3. API-Football-only fixtures are single-provider evidence, not cross-provider verification. Treat their initial verification status as `PARTIAL` or `UNVERIFIED` and confidence as `LOW`, with the returned rationale. Do not call a fixture independently verified just because it matches user-supplied names and kickoff. If exact identity remains uncertain or providers conflict, do not calculate a market-specific edge.
4. For an exact API-Football fallback fixture, the existing `/teams/statistics` integration may supply venue goal averages using the UTC day before kickoff cutoff. Use only those structured API statistics as Poisson inputs. If identity is not independently corroborated, or statistics are missing, `analyze_soccer_edge` must return unavailable probabilities and null edge values.
5. Read `get_soccer_news` for the teams. Treat headlines as reports, not verified injury or lineup records. Keep all partial form and report its actual counts and date span.
6. Build a checklist of supplied evidence and remaining topics. Investigate recent results and form, home/away performance, league standings, head-to-head history, goals scored/conceded, xG/xGA, injuries and suspensions, confirmed and predicted lineups, team news and manager statements, rest days, fixture congestion, conflicting reports, and material uncertainty.
7. When a relevant topic is missing, incomplete, disputed, or both providers fail, continue with the host's web search or browser tools if available. Search using both exact team names, competition, match date, and topic. Prefer official club and competition announcements for fixture, injury, lineup, and manager information; use reputable statistics providers for quantitative evidence. Do not scrape sites from inside PolyScope.
8. Keep official confirmed lineups separate from predicted lineups. Attribute injury reports as confirmed, reported, questionable, or speculative according to the source. Do not turn a rumor into a confirmed absence.
9. For every material browser finding, keep it separate from structured API evidence and record provider/source name, original URL, match identity, access time, publication time when actually available, verification status, confidence category, and a short rationale. Use `VERIFIED`, `PARTIAL`, `UNVERIFIED`, or `CONFLICTED` for evidence status; these labels are not calibrated probabilities. Cross-check important disputes when practical. Never invent a timestamp or statistic.
10. If both providers fail, retain each provider's reason/status and report that browser continuation depends on the host's available search/browser tools. If those tools are absent, say so and list the gaps. Never claim browser research ran without observing it.
11. Use `search_markets` to find the exact Polymarket market and outcome asset. Compare market question, teams, competition, date, and outcome mapping with the researched fixture. Read the published resolution rules. Use `get_quote` for current CLOB bid/ask depth, fillability, fees, and quote time. A midpoint or Gamma indicative price is not executable.
12. For API-Football-only fixtures, `analyze_soccer_edge` accepts host-agent attestations for fixture identity and Polymarket market mapping. A `VERIFIED` status is your claim based on source review; PolyScope does not fetch those URLs or establish their authenticity. Its output separately reports host attestation, whether supplied identity fields match the fixture, whether market fields match the supplied quote/fixture/rules, and that external source verification was not performed by PolyScope. Supply source URLs and observed/publication timestamps accurately. Browser evidence is identity evidence only and must not be passed as model statistics. For football-data.org fixtures, preserve the existing Poisson path. The model does not use market prices to estimate probabilities.
13. Only calculate edge for a market whose exact outcome mapping and published resolution rules match regulation-time Home/Draw/Away. Do not map probabilities to extra-time winners, qualification, totals, both-teams-to-score, or other unsupported rules. SELL economics remain unavailable without a position and proceeds basis. Missing identity or model inputs return unavailable probabilities and null edge values; this is analytical uncertainty, not a trade gate.
14. Present API evidence, browser findings, third-party forecasts, model estimates, Polymarket prices, and your recommendation as separate categories. Explain uncertainty, visible fillability, fees, net edge, and expected value where available. Positive edge is an estimate, not guaranteed profitability.
15. You may recommend **TRADE** or **NO TRADE** based on the evidence. This is your analysis, not a PolyScope status or eligibility gate. The user decides whether to trade. Do not call PayBox signing or trading tools without explicit user authorization.

## Provider coverage

- **football-data.org** supplies the current baseline for PL, PD, SA, and CL fixtures, results, and available recent form. Its counts and coverage labels describe only what that API returned.
- **API-Football** is an automatic, one-request fixture fallback only after football-data.org fails or returns unusable fixture data; it does not run on normal primary success. Discovery is scoped to one UTC date and competition. Exact matching requires the requested competition, normalized home/away names, and exact UTC kickoff. If that identity was not supplied or the match is ambiguous, candidates remain unverified and no team statistics are fetched. On a unique supplied identity, `/teams/statistics` may be requested for the provider's own team, league, and season IDs with the prior-UTC-day cutoff. Provider IDs remain namespaced. Missing credentials, endpoint permissions, coverage, or statistics preserve the primary error and any valid fallback fixture evidence.
- Valid empty HTTP 200 data is distinct from transport, HTTP, invalid JSON, and invalid schema failures. Empty results do not activate fallback. The output keeps both providers' diagnostics, HTTP status when available, request URL, and observation time.
- The team-statistics response is not xG. Do not infer xG/xGA from goals averages, and do not describe API-Football's `/predictions` endpoint as a PolyScope model. Any third-party forecast must be labeled with its provider.
- **TheSportsDB** free v1 endpoints have endpoint-specific limits and coverage constraints; free team-event schedules show only home events. PolyScope does not call it automatically. Use it only when it can provide a useful, independently identified piece of evidence, and preserve its event IDs separately.

## Three continuation examples

- **Form returned, xG missing:** Use the returned form and its counts, then search host-native sources for each team's xG/xGA for the relevant date range. Name and link the original statistics provider. If browsing is unavailable, say the xG topic was not independently researched.
- **Injury information missing:** Search official club updates and reputable reporting for the exact teams and match date. Separate confirmed absences from doubts, reports, and speculation; cite source URLs and timestamps and explain unresolved conflicts.
- **Browser unavailable:** Use available PolyScope evidence, state that browser research could not be performed, list material topics still unverified, and do not invent findings.

An API-Football-only fixture is single-provider evidence. A host-agent `VERIFIED` claim means the host agent reports independent corroboration; it is not a PolyScope source verification. Do not convert browser statistics into Poisson inputs. PayBox automatic skill loading and live host browser access remain unverified.
